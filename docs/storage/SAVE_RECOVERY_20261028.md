# 自动保存、检查点与开发副本减负 · 2026-10-28

## 原因

工作区停止修改 1 秒即保存，输入框失焦又立即保存；拖动节点会修改节点位置和项目时间。后端将每次变更写成完整、按内容哈希命名的 JSON，数据库无限追加版本，界面却只读取最近100条。缺少保留策略使这些自动保存长期累积；恢复入口又藏在设置的折叠区域，用户难以利用。

开发验收的重复副本来自开发流程，不是软件使用时自动建立。它们包含已交付源码、历史工作区的测试拷贝和验收产物；GitHub 已保存源码后，不应继续保留多份展开的交付目录。

## 新机制

- 当前草稿：停止编辑30秒后合并写盘，连续编辑最多等待2分钟。输入框失焦不再单独触发写盘；隐藏页面仍尝试保存，关闭未保存页面继续提示。可用“立即保存”或 Cmd/Ctrl+S。
- 自动检查点：内容变更至少间隔10分钟形成一个。节点位置、项目切换和更新时间变化不形成检查点；它们仍保存在当前草稿中，重开后布局可恢复。
- 手动检查点：可加选填备注，直接引用已保存的内容，不再次复制相同草稿。检查点建立时间独立于草稿上次修改时间；重复确认同一版本不增加副本。
- 保留最近30个检查点，草稿和检查点内容合计最多64 MiB。当前草稿始终保留；原始结构、POTCAR、冻结输入、attempt、分析结果和跨设备快照不纳入此清理。
- 底栏“保存与恢复”直接进入列表，支持命名、查看时间、预览项目与节点。选中项目后恢复为新项目，保留原项目和历史任务；沿用导入时清除执行绑定的规则，不重投计算。

磁盘修订号仍递增，用于并发写入和丢回执核对；它不再等同于一个永久检查点。每次成功发布后清理未被当前草稿或检查点引用的旧工作区 JSON。文件锁覆盖读取、保存、跨设备还原与清理；SQLite 写锁也防止清理碰到旧服务正在发布的文件。数据库提交失败不清文件，提交成功后的清理错误只记录并在后续保存重试，不把已成功的保存报为失败。

旧版本只索引一个按时间间隔抽稀的集合，首次保存/手动检查点时收敛保留范围，不复制全部旧工作区。历史读取和原始结构文件合同保持。
