## 采集方式与性能

使用服务器已有的 NVML Python 接口；不存在或读取失败时只执行一次 `nvidia-smi -q -x`，在来源服务器解析后返回小型 JSON。不会安装软件或返回完整驱动日志。MIG、禁止计算、未知进程信息或无法定位到唯一节点时不能当作空闲。旧缓存缺少明细可继续查看，并提示刷新。

实测 jutai-3：原两次 NVIDIA 查询各约 2.8 秒，PBS 节点/队列查询各约 0.02 秒，整体约 7.6 秒；已有 NVML 方式 GPU 采集约 2.95 秒、整体约 4.85 秒。本次瓶颈主要是驱动查询，不是调度器；测量不代表所有时段的网络延迟。jutai-4 无 NVML 包，使用 XML 降级方式，新增明细后整体约 1.26 秒，旧简略查询约 1.04 秒，并非每台服务器都会加速。

jutai-4 实际两张 V100 各有 VASP 进程，虽然各剩余约 27 GiB，仍须等待。两张卡的剩余显存不能合并为一个设备；利用率暂时为零也不能抵消活动进程或调度占用。

本轮逐卡采集支持 NVIDIA。AMD 可以通过已有 AMD SMI/ROCm SMI 另加适配器，当前未实现或实机验收；未知卡信息不赋予独占资格。VASP GPU 二进制及编译运行时另行核对。

依据：[NVIDIA SMI](https://docs.nvidia.com/deploy/nvidia-smi/index.html)、[VASP OpenACC GPU](https://vasp.at/wiki/OpenACC_GPU_port_of_VASP)、[AMD SMI](https://rocm.docs.amd.com/projects/amdsmi/en/latest/how-to/amdsmi-cli-tool.html)。

## 脚本使用

VASP OpenACC 提交页“使用 GPU 卡数”同步 MPI 进程数，一张使用卡对应一个 MPI 进程。预留整节点资源与实际使用数量分别冻结；不通过增加使用卡数启用共享。原脚本固定设备列表的限制保留，须选适配副本。

本机脚本库已登记“jutai-3 GPU 可选卡数（1/2/3）”，沿用实际成功任务的 NVHPC/MPI/VASP 组合。执行副本将资源派生的 NPROCS 改成所选使用数量，CUDA_VISIBLE_DEVICES 从调度器设备池或节点实际卡号取相应数量。原完成 attempt 另存 `run.gpu-selectable.pbs`，原 `run.pbs` 不变。未自动更换默认脚本。

上传的 JOB_wannier 已备份并修改：仍使用原 Intel 环境，CPU 核数来自 PBS_NODEFILE；运行时解析原环境中的 MPI/Wannier 绝对路径。软件按 W90_SEED 选择单个通道，直接使用时须设置对应 seed；不再无条件依次启动两套不存在的输入。该脚本是 CPU Wannier90，增加 GPU 数量不会将它变成 GPU 程序。真实服务器仅核验运行时可发现及脚本语法，未额外运行 Wannier 研究计算。
