# 迭代配置滚动与节点负载检测方案

## 修复与现状

独立迭代配置复用了外层 `overflow:hidden` 布局，但没有普通节点的内部滚动容器。现在迭代配置自身提供一个滚动区域，保留固定的页面上下文；物理参数、k 点、赝势、扫描范围和运行审阅均可到达。未改变参数和运行合同。

采用 `max(1, 调度器有效 CPU 数 × 0.10)` 的低负载经验门槛。56 CPU 的阈值是 5.6，64 CPU 的阈值是 6.4；它更适合多核机器上的短时残余负载。LOAD 是操作系统负载平均值，不是 CPU 利用率，因此这个 10% 是经验规则，不是“CPU 利用率低于 10%”的物理定义。参见 [Slurm CPULoad](https://slurm.schedmd.com/scontrol.html) 与 [Linux loadavg](https://www.man7.org/linux/man-pages/man5/proc_loadavg.5.html)。

## 检测规则

1. **调度与故障先判断。** 保留 Slurm DOWN/DRAIN/FAIL/MAINT/NO_RESPOND 等阻断，以及 PBS 状态、MOM 心跳、失败证据、节点排除和 GPU 原门禁。
2. **调度未分配不等于机器空闲。** 单独输出 `CPUS_UNALLOCATED`。`CPUS_FREE` 继续表示通过检查后可供本工作台派发的核数；故障或调度空闲但负载过高时置零。页面显示两种核数、LOAD 和实际阈值。
3. **只有调度空闲且负载有效、未超阈值时判为 FULLY_IDLE。** 高负载继续为 SUSPECT_LOAD；负载缺失或不可解析同样停止派发，显示待核验，不能把未知值变成零。
4. **各入口同一规则。** CLI、Web 检测、资源预览和派发前实时检查复用同一个预检脚本。Web 使用 auto；原 CLI 数值阈值覆盖保持，但非法数值在连接前拒绝。
5. **最终资源仍由原提交门禁审核。** 再核对队列、资源、脚本和目标节点；不能用旧快照作为最终提交证据。高负载候选可以等待，不强制绕过，也不自动恢复暂停／受阻计划或重投 UNKNOWN。

这些规则允许正常短时残余负载，仍阻止明显的调度外占用。高负载节点的 CPU 时间、可运行线程、I/O 等待和进程 cgroup 可按需只读诊断；本轮没有把额外 SSH/进程扫描加入每次后台轮询，也不把登录节点指标套到其他计算节点。长期混用登录服务与计算的节点建议登记用途，经管理员确认后再决定是否纳入候选；不能仅按“master”这个名称永久排除。

## 真实服务器核查边界

本轮真实服务器出现“Slurm 未分配所有 CPU，但操作系统负载远超总 CPU”的节点。直接 CPU 短采样几乎无空闲，可运行线程很多，高 CPU 进程归属系统服务而非 Slurm 作业 cgroup；这不是只靠旧平均负载推断的空闲问题。服务用途尚未核实，应由管理员核查，当前工作台阻止派发。调度器可能接受提交不代表机器适合运行新的整节点计算。

另一个计算节点的负载在两次只读检查之间下降，最终落到新阈值内，正常判为可派发；故障节点保持不可用。实际节点名、进程回执和时间戳只保存在私人验收记录。未停止进程、修改远端服务或提交研究任务。

## 验收

真实配置隔离副本使用正式的高度/布局约束，验证滚轮、键盘滚动、跨参数分组、到达扫描范围和运行审阅；不保存正式项目。真实预检验证核数与阈值、调度未分配与可派发的区分。

Shell 回归直接执行真实解析器，覆盖 PBS/Slurm、小节点阈值下限、等于/超过阈值、残余负载、严重负载、忙节点、故障、MOM 过期、缺失/非法 LOAD、CLI 覆盖及 Web 共用入口。原研究输入、历史、目录、授权及 worker 设置保持；正式装载前后核对合同。发布范围仅为滚动和容量检测，不含其他对话的改动。

公开副本后端 649 项（3 跳过）、前端 126 项、类型及构建通过。实际 Web live-capacity 和最终提交前检查均含 auto；迭代（含 Wannier 窗口）与计算链共用。已授权 ACTIVE 计划在上游、容量和额度门禁通过后按原 300 秒周期自动推进；本轮未单独授权或提交扫描验收任务。
