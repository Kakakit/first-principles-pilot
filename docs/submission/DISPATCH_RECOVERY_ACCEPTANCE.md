# 容量等待与断线恢复验收 · 2026-10-08

## 修复的问题

同一个 PREPARED attempt 在最终复核发现节点忙碌后可以继续等待，但下一轮派发没有清除旧 not_dispatched 和错误文案。若这一轮 SSH 回执丢失，状态实际为 UNKNOWN，计算链却沿用上一次 CPUS_FREE 为零的提示。链恢复还用提示文字识别 UNKNOWN，并跳过已经 BLOCKED 的步骤，即使原作业后来被找回也不能接回跟踪。

## 当前行为

- 最终容量复核使用结构化等待标记。CPU 占用、负载未恢复、GPU 活动进程保留准备记录并等待；离线或未知资源明确阻止。容量错误不再向界面暴露 Python traceback。
- SSH 连接建立失败且尚未尝试写入请求时，回执为 NOT_SENT，保留 PREPARED，等待连接恢复后复核。写入开始、部分写入、回执身份错误、远端超时或结果丢失一律不能据此认定未提交；不会自动重放远端写操作。
- 新一轮派发清除上一轮的未提交标记、等待类型与文案。UNKNOWN 显示提交回执待核查，保留额度和原服务器预留；旧回执缺少传输阶段时继续保守核查。
- 核查从原 attempt 的 .job-id 恢复精确作业号，并在同一次只读请求中检查 PBS/Slurm 状态。读回作业号不调用 qsub/sbatch。缺目录不等于没有提交，不能据此重投；实际 SSH 目标改变时拒绝核查其他服务器。
- 活动链可把找回的原作业接回跟踪；整链已 BLOCKED 时，刷新运行状态只核对原 attempt，恢复后仍由用户继续计算链。显式暂停、数值阻塞、已完成步骤、冻结输入和既有授权保留。
- 长复制的派发时限为 900 秒，普通派发为 180 秒；worker 按实际时限与会话余量避开仍在发送的任务。

## 使用

本机工作台和 worker 需要运行并保持网络连接，才能派发后续节点。合盖或断网会停止本机推进；调度器已经接收的远端作业仍继续执行。恢复联网并启动工作台后，worker 核对原作业；也可在原计算链点击“刷新运行状态”。确认原回执后，处于 BLOCKED 的整链再点击“继续计算链”。UNKNOWN 未解决时禁止重复提交。

## 验收与限制

- 440 项隔离后端回归通过，2 项跳过；85 项前端用例、类型检查和生产构建通过。
- 覆盖最终 CPUS_FREE=0、SUSPECT_LOAD、节点离线、Torque free 但 GPU 有活动进程、连接建立失败、写入失败、结果丢失、原 job ID 找回、缺目录、SSH 目标改变、长复制时限、链恢复及显式暂停。测试没有真实远端作业提交。
- 正式 Safari 原链点击刷新后，旧 CPUS_FREE traceback 被真实 UNKNOWN 回执提示取代。服务与 worker 按原配置重启，已完成结果、输入、脚本、资源及授权逐项保持；没有恢复其他暂停/阻塞队列。
- 对旧 UNKNOWN 只做了原服务器只读检查。原目录和作业号均未找回，未将“没有找到”包装成“已证明没有提交”，因此没有重投这条研究任务。原始回执、前后快照与一次性验收材料留在本机 development-backups/dispatch-recovery-20261008，不上传私人配置或研究数据。
- 本轮没有模拟休眠取代真实网络证据，也没有声称数值或物理审核通过。
