# 首次服务器配置、脚本库与提交交互改造方案

2026-10-05。状态：**已实施**。用户先审阅方案，随后明确授权实施并同步 GitHub；实际交付与验收见 [验收记录](SETUP_AND_SCRIPT_ACCEPTANCE.md)。

## 1. 采用的方案

默认采用“已有 SSH 别名 + 导入能在该服务器运行的脚本”。脚本中的 `source`、`module load`、MPI 启动器、库环境和程序命令作为本次运行方式的来源，用户不需要把这些内容重新拆成路径表单。

首次使用按“连接服务器 → 导入脚本 → 完成只读检查”引导。日常提交按“冻结输入 → 选服务器和脚本、编辑基础字段 → 检测节点、选择资源 → 预览并确认”组织。已检测后再编辑也允许：编辑只更新草稿和预览，最终派发前自动核对实时容量。

保留当前作业名称、队列/分区、walltime、核数、少用核理由、来源审阅、最终脚本预览和单次确认。现有完整运行时登记保留为高级方式；已登记服务器和旧 attempt 不迁移、不自动改写。

## 3. 首次使用的引导

### 第一步：本机与 SSH

本机 Python、软件数据目录、POTCAR 库仍按已有首次设置处理，明确区分“本机路径”与“服务器路径”。服务器连接使用系统 OpenSSH，保持终端和软件使用相同配置。

已有别名时，展示别名列表与解析出的主机、账号、端口，让用户选择，不要求重复填 IP、端口或密钥路径。别名发现支持常见 `Include` 文件；具体连接配置交给 `ssh -G` 解析，不自行实现 `Match`、跳板机和认证规则。允许手填别名，避免列表发现不完整时卡住用户。

没有别名时，提供“服务器地址、用户名、端口、别名”的短表单，生成可复制的 `Host` 配置和平台对应的操作步骤。密钥选择优先复用已有文件；创建新密钥时使用独立文件名并检查文件存在，避免覆盖原件。给出公钥安装说明或交管理员处理的入口，密码/私钥留在终端与操作系统的认证工具中。

引导按三个可识别状态展示：

1. **配置已解析**：`ssh -G <alias>` 成功；尚未连接。
2. **首次连接已完成**：用户在终端连接，核对主机指纹并完成必要认证。
3. **软件可免交互连接**：软件进程执行带 `BatchMode=yes` 的短连接测试，获得明确标记和退出状态。

第三步的首次认证测试不复用已有控制连接，以免一个已建立会话掩盖当前密钥/agent 不可用。测试应从软件实际进程环境发起；终端能登录，不代表桌面启动的软件已获得同一个 `SSH_AUTH_SOCK`。

错误给出对应下一步：网络超时指向 VPN/校园网及端口；首次主机指纹未确认指向终端；认证失败指向公钥、私钥或 agent；本机配置选项错误指向具体配置行。Mac 的 `UseKeychain` 不直接照搬到 Windows，Windows 指引使用其 OpenSSH/agent 操作。

### 第二步：导入服务器上能用的脚本

登记服务器的基本信息只需别名、调度器和工作区根目录。队列/分区优先从脚本识别，后续只读检查提供候选。调度器检测与脚本声明不一致时给出明确选择，不能静默更换。

默认选择“使用导入脚本”。MPI、环境脚本、程序绝对路径和 module 不再成为这个模式的必填字段。`source /某路径/setvars.sh`、`module load ...`、环境变量和原来的启动命令均来自脚本正文。

新设备默认根目录使用通用的 `$HOME/fpilot` 并可编辑（支持其子目录、含 `fpilot` 的专用绝对目录及原登记工作区组件），预览 `material-projects/<远端项目目录名>/...`；现有个人根目录原样保留。只读检查确认路径解析、最近存在父目录和权限，不在检查时创建目录；实际 attempt 仍由现有准备/派发流程创建。

### 第三步：一次只读基础检查

先用不依赖服务器 Python 的普通 SSH 小命令连接，再发现调度器命令及已有 `python3`/`python`。对发现的解释器查询版本和控制通道所需标准库，登记真实绝对路径，复用当前控制通道；找不到或不满足实际要求时才展开高级填写，并说明所需依赖。

登录节点可能没有计算节点的 module、MPI 或程序环境。静态识别出的路径可作为辅助提示，不能因登录节点 `command -v vasp_std` 失败而否定一个已在计算节点运行过的脚本。未安装 Python 或缺少依赖时不自动创建环境或安装软件。

首次检查不执行导入的 `source`、不启动 MPI/VASP、不投测试作业。页面分别标注“用户提供的可用脚本”“连接检查通过”“资源检查通过”“软件实际运行记录”；导入不会把用户的陈述升级成软件实测证据。

## 4. 脚本库与提交时选择

### 导入需要的信息

| 字段 | 交互 |
| --- | --- |
| 脚本名称 | 默认文件名，可改 |
| 适用服务器 | 当前 SSH 别名，可选其他已登记主机 |
| 调度器 | 自动识别 PBS/Torque 或 Slurm；识别不出时提示选择/核对 |
| 程序分类 | VASP 常规 `vasp_std`、VASP SOC/非共线 `vasp_ncl`、Wannier90、其他 |
| 可选标签/备注 | GPU、用途、来源说明等；文件名自动作为来源，不要求再填一遍 |
| 正文 | 上传或粘贴，显示原稿；保存修改副本时关联原件 |

CPU/GPU 分类沿用当前可用能力：现有脚本仍可查看和选择；复杂 GPU、多节点或混合并行资源的自动适配只在当前资源合同能够表示时启用，不能借此分类承诺新调度能力。保留现有 GPU 类型记录，补充 `vasp_ncl` 分类。

提交页直接显示“任务脚本”选择器，先按当前服务器和实际程序类型过滤，再预选其默认脚本。旁边提供查看正文、查看来源及“去导入脚本”入口。一次临时选择不会改全局默认值；保存默认仍在设置中明确进行。

分类不要求为 relax、SCF、DOS、band 分别复制一份相同脚本。普通 VASP 阶段共享 `vasp_std` 脚本；SOC/非共线阶段选择独立 `vasp_ncl` 脚本，Wannier90 使用自己的脚本和 seed 约定。链中的每种程序各选一次，阶段继承并在预览中明确显示；扫描固定本轮选择。

脚本正文不因为分类而自动从 `vasp_std` 换成 `vasp_ncl`。明显的程序冲突直接说明，例如 SOC 阶段脚本明确启动 `vasp_std`。用户可导入真正可用的 ncl 脚本或保存修改副本；不得猜测 ncl 的目录或 MPI 版本。旧记录的分类不自动重标，旧 attempt 保存的最终脚本不改。

### 哪些内容可自动修改

沿用现有基础编辑，只修改可明确映射的作业名称、队列/分区、walltime、指定节点和核数。其他调度指令、环境加载、MPI 和程序命令、输出约定保留。

必须补齐以下具体保护，避免“只改资源”实际损坏脚本：

- PBS 同一 `-l` 行的 `walltime`、`mem` 等字段分项更新，未编辑部分保留。重复或互相冲突的资源指令提示具体行号。
- Slurm 区分 `ntasks` 和 `cpus-per-task`。纯 MPI 单节点脚本可沿用核数编辑；遇到混合并行或不能映射的布局，展示原布局，不能简单把总核数写成 `ntasks`。
- 正文有固定 `mpirun -np 48` 等值时，修改核数必须显示分配核数与启动进程数的冲突。常见、明确的固定进程数可形成一份可审阅的同步修改副本；无法确定时保留原核数或提示用户修改，不能静默运行不一致脚本。
- 硬编码 `cd /旧目录` 会把计算带出本次 attempt，应提示修改为相应调度器的提交目录或移除该行，并显示差异；不静默改正文。
- 原 `trap` 与程序退出状态采集有冲突时，说明具体冲突并要求适配，不能覆盖用户清理逻辑或丢失程序退出状态。保留现有执行证据方式，不另建通用 shell 解释器。

所有差异在最终预览可见；导入原稿字节保留，Linux 执行副本的换行规范化仍沿用现有行为。

## 5. 节点检测与编辑解耦

只调整页面顺序仍不足以解决问题；用户检测后继续修改是正常操作。后端和前端必须使用相同的字段变更规则。

把当前混在一起的状态分为三类概念，复用现有记录存储，不新增一套数据库或通用工作流：

- **连接与节点事实**：实际 SSH 目标、调度器、节点状态、容量、队列/分区规则、观测时间和查询范围。
- **运行方式检查**：在高级登记模式下核对环境/程序路径；在脚本模式下保存所选脚本版本及适配检查结果。
- **本次提交草稿/已准备记录**：冻结输入、来源、脚本、名称、时间、核数、候选池、最终目录及确认内容。

名称、walltime、核数和理由不参与“节点事实是否属于当前服务器”的判断。运行时复用也不能被作业名称或 walltime 破坏。使用小范围字段投影比较；原稿和冻结产物已有的内容标识保留，不用新增整份配置哈希来解决表单变更。

| 用户修改 | 节点事实与选择 | 下一步 | 是否强制重新检测节点 |
| --- | --- | --- | --- |
| 作业名称、walltime、备注、少用核理由 | 保留 | 本地校验、更新脚本和预览；超过已知队列时限立即提示 | 否 |
| 核数、同一服务器内节点/候选池 | 保留事实，保留仍合法的选择 | 对已知容量和进程数做本地校验；更新受影响脚本 | 否 |
| 同服务器、同调度器切换导入脚本 | 保留 | 重做脚本适配/程序匹配，重生成预览 | 否 |
| 队列/分区 | 保留适用的事实与选择 | 按已知队列规则本地复算；缺规则时自动补查该队列/分区 | 否；新分区超出旧查询范围时自动补取相关节点 |
| 环境脚本、module、MPI、程序路径 | 保留同一目标上的节点事实 | 仅运行方式检查失效，按需重新检查；预览重做 | 否 |
| 工作区根目录/远端项目目录名 | 保留 | 路径预览和目录权限/身份检查重做 | 否 |
| 冻结输入、来源版本、std/ncl 类型 | 保留同一目标上的节点事实 | 输入和程序匹配、脚本预览、准备确认重做 | 否 |
| SSH 别名、实际目标/账号/端口/跳板改变，或调度器改变 | 原事实不适用，清除原节点/候选池 | 查询新目标；分支已有绑定规则仍生效 | 是 |
| 手动点击“刷新节点” | 用新事实更新 | 保留仍合法的选择，说明被移除项原因 | 用户主动刷新 |

表中“保留”不表示继续使用旧的最终提交确认。凡影响本次作业内容、来源、脚本、资源或路径的修改，都使最终预览/准备确认失效；用户重新预览确认，但不必再手动检测同一服务器。

检测结果显示“上次检测时间”和“派发前将自动复核”。事实过旧时允许作为候选和预览依据，不能当作占用许可；提交前由后端查询最新状态。名称等连续输入过程中不发 SSH 请求，也不自动轮询节点。

程序切换后已发现的 CPU 节点事实可复用，但运行方式检查按实际程序分别处理。GPU 或新分区需要额外事实时，只补取相关范围；不能把 CPU 检测结果当作 GPU 资源证据。

## 6. 日常提交流程及最终派发

页面保留四块，顺序调整为：

1. **输入**：选择已冻结输入，保留现有来源与输入审阅。
2. **服务器与脚本**：显示分支服务器，直接选择已导入脚本，编辑名称、队列/分区和 walltime。
3. **节点与资源**：检测/刷新节点，选择节点或候选池，编辑核数，保留少用核理由。
4. **预览与提交**：展示本次资源、路径、来源和最终脚本，确认一次。

核数既可先填写请求值，也可在看到节点容量后修改。选择节点后才填确定节点字段；不会要求用户编辑不存在的节点。点击预览后返回修改，保留同一服务器仍适用的节点信息和选择。

准备阶段冻结最终脚本及实际资源。确认按钮进入已有后端派发流程：核对本次记录和来源 → 实时复核所选节点与队列 → 执行现有目录/输入保护 → 单次 `qsub`/`sbatch` → 记录确切 job ID/回执。能在现有一次非重放派发请求内完成的检查，不额外复制成多个 SSH 往返。

实时状态变化的处理保持可解释：

- 单任务所选节点已繁忙/容量不足：明确显示没有调用调度器，保留草稿、输入和脚本；更新容量并允许改选节点或稍后重试。不能自动修改已确认的核数/脚本或跳到另一台服务器。
- 链/扫描：保留已授权候选池和脚本版本；临时繁忙继续等待，按候选池选择已预览过的适配资源。改变池、脚本、输入或授权资源后重新预览授权。
- `UNKNOWN`：保留并核对原回执和 job ID，不自动再次提交。

保存“默认脚本/默认名称”只影响后续草稿。已准备或已授权任务使用冻结的脚本和运行方式版本，不能只因全局默认名称改变而重新扫描节点或改写任务。真正改变连接、所引用运行方式版本或提交内容时，要求重新准备/授权；旧记录保留其合同。

## 7. 后端与界面实施范围

| 工作项 | 主要文件 | 交付边界 |
| --- | --- | --- |
| 连接向导与分阶段登记 | `site_registration.py`、`SiteRegistration.tsx`、`LocalSetup.tsx`、`SettingsWorkbench.tsx` | 明确区分配置解析/免交互连接；脚本方式不要求 MPI/setvars 路径；发现真实控制通道 Python |
| 脚本分类与适配 | `job_templates.py`、`JobTemplatePanel.tsx`、`workbench_settings.py` | 复用导入/副本/回收；补 ncl 分类；按脚本取运行方式；保留未编辑资源指令 |
| 检测、校验和缓存 | `servers.py`、`executionUi.ts`、`submissionDefaults.ts` | 容量与运行方式分开；保存服务器不必提前填完整 VASP 运行时；内置生成脚本仍按登记模式校验 |
| 提交选择与变更规则 | `ServerPanel.tsx`、`ExecutionPanel.tsx`、`WannierPanel.tsx`、`ChainPanel.tsx`、`ScanPanel.tsx`、`WannierScanPanel.tsx` | 所有提交页遵循同一规则；链按程序类型选择脚本；基本编辑保留 |
| 最终派发与快照 | `execution.py`、`wannier_execution.py`、`chain_runs.py`、`scans.py`、`fast_dispatch.py` | 脚本模式不再强行依赖高级 VASP 路径；保留实时资源和一次派发；分类不能替代实际程序约束 |

建议按三步实施：

1. **先修编辑导致检测失效**：分离事实与草稿变更，覆盖单任务、链、两类扫描和 Wannier90；保留节点/候选池，统一预览失效规则。这一步独立改善现有使用体验。
2. **连通脚本式首次配置和提交选择**：服务器最小登记、控制通道发现、分类、脚本方式校验、提交页选择及资源保留一起完成。只隐藏表单而不改后端必填约束，不能算交付。
3. **调整四块顺序并做完整空工作区验收**：校验不同程序脚本、首次配置错误反馈、返回编辑、候选池等待和最终自动复核。完善帮助文字，不附带主题重做、扩展重构或新调度平台。

不预先引入新的 SSH 库、shell AST 解释器、依赖注入框架或重复状态数据库。系统 OpenSSH 配合现有 Python subprocess/连接层足够表达这次需求。脚本分析只覆盖需要编辑的明确字段；无法确定的部分交给原稿与可核对差异。

## 8. 验收与必要验证

实施复用已有测试文件，必要用例放在对应领域；实际检验、服务加载与证据边界见验收记录。下表为设计验收要求。

| 场景 | 验收结果 |
| --- | --- |
| 空工作区、用户只知道账号/地址和一份 PBS 或 Slurm 脚本 | 能完成引导、连接、导入、选择与预览；不需要用户知道 setvars/MPI 路径 |
| 特殊 SSH 端口、常见 Include、Mac/Windows 配置差异 | 正确解析有效配置；指引区分平台；仅解析不得显示为免密已验证 |
| 终端已登录但软件 agent 不可用 | 软件测试给出认证问题，不误报连接就绪 |
| 登记后发现服务器没有满足要求的 Python | 清楚指出控制通道依赖与手动路径入口，不自动安装 |
| 检测后连续编辑名称/walltime/核数，或切换同服务器脚本 | 编辑期间 SSH 请求数为 0；节点选择仍在，预览/确认按需失效 |
| 修改核数或 walltime 超出已知条件 | 本地立即指出原因，未触发强制节点扫描，提交仍可被最终实时复核阻止 |
| 更换服务器或实际 SSH 目标；更换分区 | 前者不能沿用旧节点；后者仅补取缺少的规则/范围，候选选择按适用性处理 |
| PBS 混合资源行、固定 MPI 进程数、Slurm 线程布局、硬编码工作目录 | 未修改字段保持；不能映射或资源冲突明确显示；原稿不变，无静默参数丢失 |
| 普通与 SOC 阶段脚本不同，链混合两类阶段 | 使用显式分类和冻结选择；正文不被自动替换，缺合适脚本时指出具体阶段 |
| 最终确认时节点刚变忙；双击/超时 | 实时保护生效；一次授权至多一次调度提交；UNKNOWN 不重投 |
| 默认脚本变化与旧 attempt | 新草稿按新默认；历史脚本、旧 job ID 和来源保持；已授权内容不悄悄改变 |

功能验收使用独立空数据目录、端口和浏览器存储，实际走 UI/API；测量编辑网络请求数及检测/准备耗时，明确把模拟和真实服务器证据分开。针对 `test_servers.py`、`test_runtime_cache.py`、`test_job_templates.py`、提交/执行恢复及所改链/扫描用例运行必要检查；字段编辑验证看请求与状态，不新增一组镜像测试。业务前端改动后做类型检查和一次生产构建。

由于第二步改变核心派发的运行方式与脚本来源合同，合并交付前进行一次对应的完整业务回归及针对性人工审核；不是每个中间文案调整都重跑全量。Windows 原生免交互连接和真实集群提交需要对应环境与明确单次授权，不能由本机模拟替代。

## 9. 外部依据与实现取舍

已查官方说明和维护中的上游项目。`ssh -G` 负责解释配置后退出；`BatchMode=yes` 禁止密码/指纹的交互提示，适合软件连接测试。采用现有系统 OpenSSH 的薄适配，使终端指令可复现软件连接；没有新增运行库或随包分发 SSH 二进制的成本。OpenSSH 的源码、维护和许可可由上游核对，后续也不依赖某个新解析库。

- [OpenSSH ssh：-G 等选项](https://man.openbsd.org/ssh.1)
- [OpenSSH ssh_config：BatchMode、IdentityFile、Include 等](https://man.openbsd.org/ssh_config.5)
- [OpenSSH Portable 上游与许可](https://github.com/openssh/openssh-portable)
- [Microsoft：Windows OpenSSH 密钥和 agent](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement)
- [Slurm sbatch：ntasks、cpus-per-task 等资源语义](https://slurm.schedmd.com/sbatch.html)

不采用新的 SSH 库来重写这部分：当前系统命令已满足配置兼容和免交互测试，增加库会带来第二套认证/代理配置维护；这是结合现有代码的实现取舍。Slurm 的任务数和每任务 CPU 数须按官方语义分别处理，不能因 UI 都叫“核心数”就混为一个值。
