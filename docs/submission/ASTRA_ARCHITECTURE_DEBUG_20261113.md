## P2：远端已清理会误拦截仍存在的本地分析文件

位置：`backend/file_transfers.py:224`。

产物目录 `backend/artifact_refs.py:81-100` 在远端清理后仍正确保留本地分析产物的位置。收集逻辑会优先选本地位置，但运行传输时无条件检查生产者的远端清理标记，导致本地文件也失败。

补充复现使用 `FileTransferTests` 的隔离本地文件，建立 producer_kind=analysis 的本地传输任务；模拟生产者未回收、远端清理标记为真，调用实际 `run`。返回：

```text
FAILED 来源已回收或清理，请先恢复原记录
```

预期是正常复制现存本地文件。这个场景没有丢失数据，但用户无法通过文件收集入口获取本来可用的副本，点击继续仍然失败。

建议仅对实际选择的 remote 来源检查远端清理状态；local 来源保留所属记录状态、文件存在和版本检查。补一项“远端清理后仍能收集本地分析输出”的回归用例。复现使用模拟清理标记，不是实际执行远端删除。

## P2：历史记录逐条重复轮询项目级传输列表

位置：`src/FileCollection.tsx:13-14`、`src/ExtensionPanel.tsx:125`。

每个 FileCollection 挂载后立即开始约两秒一次轮询，接口返回当前项目全部传输任务，再由每个组件自己过滤。ExtensionPanel 在每条历史记录的 details 内挂载 ExtensionResult；details 折叠不会卸载组件。HistoryList 默认显示 5 条，查看更多后会挂载更多记录。因此，即使没有活动传输，多条已完成历史也会重复请求同一列表。

这项是调用链静态确认，未做浏览器流量/内存压力实测；不能据此声称已经复现卡顿或内存泄漏。

建议项目层只保留一份传输列表和轮询，子组件按生产者筛选共享结果；有活动任务时刷新，终态后停止定时刷新，创建/重试时重新启动。至少先做到只有展开记录加载，且无活动任务时不持续轮询。
